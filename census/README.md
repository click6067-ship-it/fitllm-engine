# Local LLM Fit Census v1 — 2026-10-23

**13,804 verdicts**: 34 models × 104 devices (47 GPUs + 57 Mac configs) × per-platform quant tiers.
Each row is generated by [fitllm-engine](https://github.com/click6067-ship-it/fitllm-engine) from architecture inputs pinned to official `config.json` files. Runtime and OS reserves remain documented estimates. **Reproduce it yourself: `npm run census`.**

Assumptions: context = min(8K, model max) · KV cache F16 · platform reserve/headroom per engine. Interactive per-combo pages: [fitllm.run/can-i-run](https://fitllm.run/can-i-run).

## Full data

- [`census-v1.csv`](census-v1.csv) / [`census-v1.json`](census-v1.json) — every model × device × quant verdict with the full predicted breakdown (`predicted_total_to_run_gb` = weights + KV + runtime + reserve — what the verdict uses; `predicted_resident_weights_gb` = quantized weights **plus ~12% runtime weight overhead** (non-quantized parts, buffers; none on one GB10 unit, where GGUF weights count at file size) — the number resident-weights measurements should be compared against; `predicted_param_gb` = quantized weights alone) and max context. Machine-readable; import it, chart it, cite it.
- **Measurements are typed** (from [`fixtures/measured.json`](../fixtures/README.md), community PRs): `measurement_kind` says what was measured. `idle_resident` readings (e.g. oMLX `actual_size`) are a resident-weights **floor** — compare them to `predicted_resident_weights_gb`, not to the total; only `system_total_peak` is comparable to `predicted_total_to_run_gb`. An idle_resident value below the predicted total is expected, not an over-prediction. Ledger holds 13 entries; 6 join this census (exact model+device+quant match required — the rest cover models/devices outside the catalog or carry unconfirmed attribution).
- **Structural premise disclosed — `ple-llamacpp-non-gpu-residency`**: every discrete-GPU row for `Gemma 4 e2b` and `Gemma 4 e4b` excludes the per-layer-embedding (PLE) tensor — 2.349B of e2b's 5.1B and 2.819B of e4b's 8B parameters — from `predicted_param_gb`, `predicted_resident_weights_gb`, `predicted_total_to_run_gb`, `free_gb`, `max_context` and the verdict, because the pinned llama.cpp/GGUF path assigns that input-layer tensor to CPU/host buffers rather than the discrete GPU's memory pool. So `params_b` × bytes-per-weight will not reconcile against those columns for those rows (at Q4_K_M the excluded weights are ~1.34 GB for e2b and ~1.61 GB for e4b; at FP16 ~4.38 GB and ~5.25 GB). The excluded bytes still need host/system memory that this census neither budgets nor verifies; a runtime that loads PLE onto the accelerator invalidates those rows; the GB10 unified-memory rows (DGX Spark 128GB, 2× DGX Spark 128GB, 4× DGX Spark 128GB) and the Mac rows (Apple unified memory) count the full weights. No row treats SSD/NVMe streaming, expert paging or swap as capacity. Premise text and pinned sources: [Structural premises](https://github.com/click6067-ship-it/fitllm-engine#structural-premises).

- **Structural premise disclosed — `gb10-unified-memory-reserve`**: the `DGX Spark 128GB` rows count GGUF weights at file size (no 12% weight overhead; `predicted_resident_weights_gb` = `predicted_param_gb`), plus 15% of the KV cache and the context-scaled activation allowance, and `reserve_gb` is the 13.3 GiB DGX OS and runtime reserve. That is calibrated on public llama.cpp and Ollama allocation logs on GB10 with flash attention on, the default in both ([fixtures](../fixtures/measured.json)); with flash attention off llama.cpp holds the full attention scores, and single-unit vLLM adds CUDA-graph memory and a pre-allocated KV pool — neither is budgeted, nor are llama-server's host prompt cache and context checkpoints.
- **Structural premise disclosed — `gb10-cluster-tensor-parallel`**: the rows for `2× DGX Spark 128GB` and `4× DGX Spark 128GB` assume one model split across the units by vLLM with Ray or TensorRT-LLM (tensor parallel equal to the unit count; NVIDIA supports two units by a direct QSFP cable and four through a RoCE switch). `reserve_gb` is the per-unit DGX OS and runtime reserve times the units, activation buffers are counted per unit, and `kv_cache_gb` includes the replication when a model has fewer KV heads than units or uses an MLA latent cache or DeepSeek's compressed cache. Ollama and LM Studio use one unit, so these rows do not apply to them.
- **Structural premise disclosed — `deepseek-compressed-sparse-kv`**: `kv_cache_gb` for `DeepSeek-V4.1-Flash-1017`, `DeepSeek-V4-Flash`, `DeepSeek-V4-Pro` counts the buffers DeepSeek's reference inference code allocates — a sliding-window cache on every layer, a compressed cache plus indexer keys only on the layers that compress their own KV (one entry per compress_ratio tokens), the compressors' fp32 state, V4.1's Engram token history and a 512 MiB indexer prefill workspace per unit (vLLM's default bound) — at F16. `params_b` is the whole checkpoint (Engram tables, vision tower and MTP/DSpark draft weights included, all resident), so it is larger than the backbone figure on the model cards, and V4.1's 196.6B Engram tables are never counted below their FP8 storage (8.25 bits with scales), so its Q4 rows do not reconcile with `params_b` × 4 bits.
All figures are estimates; real usage varies with runtime, driver and OS state. Verdicts: ✅ fits comfortably · ⚠️ tight · ❌ won't fit.
